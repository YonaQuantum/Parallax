# 前端需求契约

这份文档描述 Radar 应该给 PARALLAX 前端提供什么，而不是规定 Radar 内部怎么实现。

## 首页

首页展示的不是 Radar 自身，而是外部世界的变化。

需要数据：

- 最近 3 到 6 条 World Signals：
  - GitHub 上快速增长或异常活跃的开源项目
  - 新开源模型、新 RAG 工具、本地 AI 工具
  - 游戏与交互领域出现有趣机制、工具链或开源技术
  - 硬件、嵌入式、机器人、传感器和 DIY Hardware 相关项目
  - 创作与媒体领域的图形、音乐、Blender、Shader、音频工具变化
  - 科学与宇宙领域的 NASA、ESA、JWST、系外行星、宇宙生命和科学哲学资料
- 每条 Signal 的阶段：`NEW`、`RISING`、`ACTIVE`、`COOLING`。
- 每条 Signal 的原始来源。
- 每条 Signal 的简短解释：为什么值得看。Radar metadata 使用 `whyItMatters`，并在第一阶段兼容写入 `whyInteresting`。

已有接口：

```txt
GET /api/observatory/stream
```

首页没有真实 Signal 和社区新内容时，不渲染 `New` 区域，不显示 Radar 状态占位。

## 观测台

观测台需要展示 World Signals，而不是 Radar 自身。

需要数据：

- 研究信号队列。
- 灰色干扰波队列。
- 高热度外部事件。
- 深层归档入口。
- 每条成果的骨架数据，用于前端做硬边图形、峰值线、频谱块和坐标切片。

当前主站已有 `IngestedArtifact`、`KnowledgeStream`、`DerivedSkeleton`，Radar 需要把资料通过 `/api/radar/ingest` 写入。

## 探索页

探索页需要把 Radar 结果混入真实内容，但不能伪装成用户发布。

建议分区：

- 社区内容：用户发布的文章、文档、视频、图文。
- World Signals：Radar 标记的外部资料。
- 工作室素材：适合游戏工作室进一步实验的项目、论文、机制或工具。

每条 Radar 观测至少需要：

- 标题
- 原始 URL
- 领域
- 热度
- 质量分
- 干扰标记
- 为什么值得看
- 适合哪个板块
- 可执行下一步

## 游戏与交互板块

游戏与交互不只收游戏新闻，应偏向“能长出工作室能力”的资料。

Radar 需要重点判断：

- 是否有可复用玩法机制。
- 是否有开源工具链价值。
- 是否可转化为原型。
- 是否和创作与媒体、光谱科学、硬件交互或科学与宇宙交叉。
- 是否适合作为社区成员共创任务。

子方向：

- 游戏引擎
- 工具链
- 玩法机制
- 程序化生成
- 实时图形
- 声音交互
- 光谱科学
- 科幻设定与宇宙生命

## “好玩项目”的判定字段

Radar 不要只看总 star，要结合：

- star 增速
- 最近提交活跃度
- issue / discussion 活跃度
- demo 可运行性
- 文档质量
- 代码可读性
- 是否和 PARALLAX 的方向有关
- 是否能给游戏工作室带来原型灵感

推荐输出：

```json
{
  "whyInteresting": "这个项目把 shader 编辑和实时预览做成可嵌入工具，适合做工作室内部材质实验台。",
  "studioPotential": "prototype",
  "nextAction": "拉取 demo，验证 Linux + GPU 工作站 环境下的运行状态。"
}
```

## 交互需求

前端希望 Radar 数据能被这样使用：

- 光环周围短暂亮起警示黄，表示有新信号。
- 领域轨道根据热度改变边框强度。
- 灰色干扰波以低透明、硬边噪点出现，不自动占据主视觉。
- 高热项目进入“工作室候选”轨道。
- 用户可以把 Radar 观测转为创作草稿或共建任务。

## 不要做

- 不要用假数据制造热闹。
- 不要把 Radar 观测冒充社区成员原创。
- 不要展示 Radar 在线状态、遥测或调试信息作为装饰。
- 不要直接展示未经处理的大段抓取全文。
- 不要让 Radar 自动发布正式内容。
- 不要做聊天气泡式助手。
