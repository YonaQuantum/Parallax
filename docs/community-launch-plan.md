# 社区融合体验与首发方案

记录日期：2026-09-07。本文基于当日源码检查和维护者讨论；它是实施与验收方案，不代表功能已经上线，也不代替生产环境验证。

## 已确认的产品方向

- 六大领域属于同一个社区，共享导航、搜索、标签、账号、阅读和讨论体验。
- 首页、探索、观测台与领域列表中的内容条目先进入站内详情；原文通过详情里的明确链接访问。
- 详情首屏沿用首页视觉：桌面端左侧文字、右侧图片，图片向文字区域渐隐；正文和评论位于下方。
- 外部 Signal 也有可阅读的中文图文摘要和成员评论，保留来源及机器整理身份。
- 首发直接开放邮箱注册，访客可阅读，完成邮箱验证后参与评论。

以下技术结构、发布顺序和验收条件是建议实施方案；本次只落文档，不修改数据库、应用或部署配置。

## 统一体验如何融合领域

六大领域继续作为浏览入口，专题和标签表达交叉关系。Arch 归入“编程与开源”，太空前沿归入“科学与宇宙”；涉及开源飞控的条目同时可以出现在硬件、编程和航天主题中，但只有一个详情地址和讨论区。

用户路径统一为：

```text
首页 / 搜索 / 领域 / 专题 / 观测台
                  ↓
          同一条目的站内详情
                  ↓
       阅读 → 讨论 → 相关条目 / 原文
```

- 导航、字体、强调色、卡片行为、登录提示在各领域保持一致。
- 搜索共用一个入口，可按领域、标签、社区内容或外部信号筛选；同一条目在一次结果中只出现一次。
- 相关内容根据共同主题与实际关联选取，允许跨领域；第一版用标签规则即可，无内容时不占位。
- 同一条目从不同列表进入时，共用浏览地址、评论计数和后续收藏状态；不能为每个板块复制记录。
- 首发统一基本评论体验。收藏、回复通知、专题订阅后续接入同一账号体系，不由各专区单独实现。
- 社区文章继续展示作者；外部条目展示来源和“Radar 整理”。成员延展文章通过引用关联原 Signal，不覆盖它。

## 站内详情与视觉约定

桌面端结构示意，比例由真实标题长度和图片裁切确定：

```text
统一导航 / 返回列表
┌─────────────────────────────────────────────┐
│ 领域 · 来源 · 日期                            │
│ 中文标题与导语          渐变过渡 → 来源图片     │
│ 标签 · 阅读原文                               │
└─────────────────────────────────────────────┘
可读正文：事实摘要、关键变化、必要图片与图注
来源依据 / 更新记录（有内容才显示）
讨论：登录提示或输入框、成员评论、分页
相关内容（有真实关联才显示）
```

- 渐变只用于首屏，长正文使用舒适行宽，不把整个文章塞入左右两栏。
- 手机端按标题、导语、图片、正文、评论上下排列，图片不压住文字；无图或图片失效时自然退化为纯文字首屏。
- 图片预留尺寸，内容图片提供说明和替代文字；装饰图不重复朗读。保证文字对比度和键盘操作。
- 正文不重复首页短摘要来凑长度。资料只有一小段时，就呈现短内容；图文丰富程度由证据决定。
- 原文入口清楚可见，不把外链藏起来；分享按钮分享站内永久链接。
- 未登录用户阅读与查看评论不受阻，评论输入位置提示登录。登录后返回原条目；返回地址仅允许站内路径。

## Radar 图文输出与生命周期

Radar 在后台生成并保存结果，详情读取已保存版本；读者打开页面不触发现场模型推理。采集异常时继续展示上一次可用结果及更新时间。

建议新增的展示契约包括：中文标题、短导语、段落/列表/图片等受限内容块、来源条目、来源发布日期、采集时间、摘要修订时间、图片来源与说明、事实依据及修订记录。具体字段在实施时更新 Radar schema 和 ingest API 文档。

- 模型生成受校验的结构化内容，不生成或执行任意 HTML、JS、TSX、MDX。抓取正文中的指令也不能改变采集和发布权限。
- 标题、摘要及数字结论能回到对应来源；低证据条目不硬扩写。Arch 风险结论区分官方确认与待复核；航天内容区分计划、试验、验证和实际运行。
- 展示短摘要和必要引用，不镜像外部全文。外部图片是否可展示按来源授权和使用规则处理；`og:image` 只提供候选地址，不代表已取得转载授权。
- 第一版沿用外部图片 URL 策略，不自动镜像。不能使用的图片直接省略；未来媒体缓存通过独立存储扩展接入。外链图片保持不发送 referrer，并说明访问第三方图片仍会产生第三方请求。
- 图片/来源 URL 限定可接受协议；如以后增加服务端图片代理，必须限制主机和重定向目标，防止访问内网。
- 普通过期 Signal 从新信号流退出后，已有站内地址和讨论仍保留，展示归档或过时提示。安全下架采用受控说明页；不能因采集刷新、去重或过期回收连带删除成员评论。
- 同来源更新保持稳定记录 ID。跨来源重复条目合并时保留旧地址跳转与讨论归属；模型不能直接执行不可逆合并。

Arch 专题先接官方新闻、安全通报与重点 Wiki 页面差异；AUR 构建文件只读取比较，不执行，也不作“已扫描所以安全”的承诺。太空专题先接可靠任务与技术更新，按任务持续追踪，避免常规发射消息挤占整个首页。

## 前端与数据实现建议

继续使用 **Next.js + React + TypeScript / TSX + Tailwind / CSS**。TSX 是带类型的组件源码，构建与渲染后浏览器获得 HTML、CSS 和必要的 JavaScript。图文渐变由 CSS 完成，不需要换框架。

页面默认在服务端读取与渲染数据，评论表单、收藏等交互只在局部使用客户端组件，符合 [Next.js 的组件分工](https://nextjs.org/docs/app/getting-started/server-and-client-components)。实现前以已安装版本 `node_modules/next/dist/docs/` 的对应指南为准。

建议保留 `/content/[slug]`，新增 `/signals/[id]`；两种路由共用阅读布局、内容块、来源展示和讨论组件。路由形状可以不同，交互和视觉应一致。外部页面使用数据库原始稳定 ID，不用可变化的标题或列表临时前缀生成身份。

业务组件仍放在 `apps/web/src/features/<domain>`，鉴权与持久化放在 `apps/web/src/server`。统一展示不要求把外部资料伪装成 `Content` 或把业务全部塞到一个组件里。

评论建议引入共用 `DiscussionThread`：每个线程唯一关联一篇社区内容或一条外部资料，评论挂在线程上。实施时需要：

1. 为两类目标保留真实外键、唯一约束，以及“恰好关联一个目标”的数据库检查约束。
2. 回填现有文章评论的线程，保留评论 ID、作者、时间与回复关系；切换后再移除旧的必填关联。
3. 回复必须属于同一线程；所有写入检查目标可见性、账号状态、权限与限流。
4. 对归档、下架、合并和账号删除定义保留策略，避免级联删除误伤讨论。
5. 同步 Prisma migration、架构文档与相关 API 契约，验证旧数据迁移和回退策略。

这是待实施模型提案；当前 schema 没有 `DiscussionThread`。收藏与通知后续沿用同样的目标语义，避免重复维护两套产品行为。

## 开放注册与用户管理

首发使用邮箱和密码，用户名可用于登录；邮箱验证完成后才获得社区写入权限。先保证此流程完整，GitHub OAuth、第三方绑定与更丰富的个人设置后续扩展。

| 身份 | 建议权限 |
| --- | --- |
| 访客 | 阅读公开详情、评论与搜索结果 |
| 未验证账号 | 验证与重发邮件、找回账号；不能发布、评论或上传 |
| 已验证成员 | 评论、管理自己的内容；发布与上传受频率和配额限制 |
| 版主 | 处理举报、隐藏违规内容、禁言/封禁普通成员；不能提升角色或处置主理人 |
| 主理人 | 管理角色、站点设置与管理操作；保留可核查的操作记录 |

角色表示权限，账号状态表示能否使用，两者分离。`IdentityCard.status` 是卡片状态，不能替代账号封禁；封禁必须在服务端生效并撤销已有会话。

账号菜单首发至少提供个人页、账号设置和退出。管理入口首发至少提供用户列表/状态、封禁与解封、评论隐藏与恢复、举报处理和操作记录。不要把直接改数据库当成常规社区管理方式。

继续保留本地数据库会话边界，认证层单独评估采用维护中的认证库与补齐现有实现的成本；[Next.js 官方建议优先使用认证库](https://nextjs.org/docs/app/guides/authentication)。无论选择哪种方式，都要通过以下验收，不以“已经有登录页”认定可开放注册。

## 首发前必须完成的验收

以下均未在本次执行或通过；完成实现后逐项记录结果。

| 项目 | 源码发现或缺口 | 验收要求 |
| --- | --- | --- |
| 注册恢复 | 先创建用户再发邮件，发送失败会留下未验证账号；没有重发入口 | 邮件失败可重试，同邮箱不重复建号，用户看得懂下一步 |
| 注册并发 | 用户名/邮箱与身份卡序号先查后建；序号基于计数 | 并发创建碰撞能重试或返回受控提示，不丢账号、不暴露数据库异常 |
| 验证链接 | 过期和使用状态已有检查；单次消费需要并发条件保护 | 过期、重复点击、重发旧链接与并发请求都有明确行为 |
| 密码找回 | 未找到完整流程 | 随机单次 token、有效期、哈希保存；重置后撤销旧会话；存在与不存在账号返回一致提示 |
| 密码长度 | 当前允许 128 字符，但 bcrypt 有 72 字节输入边界 | 注册/改密以 UTF-8 字节处理边界或迁移哈希方案，不能静默截断；保留旧密码兼容策略 |
| 会话 | 退出函数未接出；没有全会话撤销和账号封禁检查 | 退出后 cookie 与数据库会话失效，过期/封禁/改密后旧会话不能继续写入 |
| 防滥用 | 未找到注册、登录、发信、评论的应用限流 | 按账号与可信客户端地址限制；多进程共享计数；验证代理头不可伪造，超限可恢复 |
| 评论权限 | 当前仅校验登录和内容存在，未检查目标发布状态 | 不能向草稿/不可见/关闭讨论目标写入；不能越权修改或管理他人评论 |
| 评论管理 | 未找到举报、隐藏/恢复、分页完整流程 | 两类条目统一可管理，普通成员不能调用版主操作；分页不漏掉已有评论 |
| 个人资料 | 成员查询未按邮箱验证状态过滤 | 未验证账号不进入公开成员目录；公开返回对象不含邮箱、token 或密码哈希 |
| 上传 | 依赖客户端 MIME；保留原扩展名；单文件上限 512MB | 服务端核验文件实际类型并规范扩展名；代理与应用限制请求体、频率和配额，错误文件不能作为可执行网页返回 |
| 外部详情 | 当前列表主链接主要为外链，无 Signal 评论关系 | 所有内容列表进入稳定详情；来源按钮才外跳；跨领域进入同一条目看到同一讨论 |
| 图文降级 | 新布局与结构化正文未实施 | 无图、坏图、短摘要、长标题、移动端、模型不可用时仍可正常阅读 |
| 生产恢复 | 本次未检查线上配置与实际收信 | HTTPS 下真实邮箱注册/验证/找回/退出完整通过；数据库和上传备份完成一次恢复演练 |

密码恢复规则参考 [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)；bcrypt 输入边界参考 [bcrypt.js 官方说明](https://github.com/dcodeIO/bcrypt.js)。这里记录的是源码问题与验收方案，不是已验证的攻击报告。

公开注册前还应明确社区规则、公开资料范围、举报和账号注销入口。日志不得记录密码、原始会话或验证 token；账号删除与讨论保留/匿名化规则应提前确定。

## 建议交付顺序

1. **账号与管理闭环**：开放注册、邮件恢复、密码找回、退出、限流、角色与账号状态、评论治理及上传限制。
2. **统一阅读与讨论**：共用详情组件、Signal 详情路由、评论迁移、全站卡片内链、移动端与归档行为。涉及新评论入口的验收在此阶段复测。
3. **两项专题首发内容**：Arch 与太空分别接入少量可信源，使用同一详情体验；只发布真实、可追溯的图文摘要。
4. **上线后增强**：跨领域相关内容、收藏、通知、订阅、OAuth、AUR 更细粒度差异审阅与任务时间线。

第一至三阶段完成并通过验收后再开放完整社区。上线时间紧时缩减第四阶段及内容源数量，账号恢复、内容治理和统一阅读链路仍需完成。

生产配置与操作步骤见 [1Panel 部署说明](deployment-1panel.md)。实现后的代码检查应运行 lint/build；身份与权限、评论迁移和异常恢复需要相应集成测试，生产收信与备份恢复另行验收。本次文档提交只检查内容一致性、链接、差异格式与敏感信息，不宣称应用测试或上线验收通过。
